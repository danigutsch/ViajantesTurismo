# FOSS compliance

This repository is licensed under the [MIT license](../LICENSE.txt). Package metadata uses the SPDX
license expression `MIT` unless a project explicitly documents a different license.

## Dependency license policy

Prefer permissive dependencies with clear provenance and SPDX license evidence.

Allowed for routine dependency updates:

- `MIT`
- `Apache-2.0`
- `BSD-2-Clause`
- `BSD-3-Clause`
- `0BSD`
- `ISC`
- `PostgreSQL`
- `Zlib`
- `Unlicense`
- `CC0-1.0`

Denied for routine dependency updates:

- `AGPL-*`
- `GPL-*`
- `LGPL-*`
- `SSPL-1.0`

Escalate before merging when a dependency has an unknown, custom, mixed, reciprocal, source-available,
copyleft, commercial, or weak-provenance license. Scanner output is evidence, not final legal advice.

The `Dependency Review` workflow enforces the automatable portion for pull requests by failing on
moderate-or-higher advisories and by allowing only the routine-license set above for changed
dependencies. Update this document and `.github/workflows/dependency-review.yml` together when the
routine license set changes.

## Vulnerability severity gates

Dependency Review fails pull requests on `moderate` or higher advisories because it evaluates newly
introduced dependency changes. NuGet audit remains at `high` in `Directory.Build.props` because it runs
for all projects during restore/build and may include advisory noise unrelated to the current change.

Treat the thresholds as intentionally different until the repository has reviewed full-solution NuGet
audit volume. Lowering NuGet audit to `moderate` is a separate policy change because it can affect every
developer build.

## Third-party notices

Do not vendor third-party source, generated files, templates, images, fonts, or binary assets without
recording provenance and license evidence in the same pull request.

For NuGet dependencies, `SharedKernel.Versioning.Tool prepare-release` reads resolved `packages.lock.json`
files and writes:

- `artifacts/release-prep/third-party-attributions.json`
- `artifacts/release-prep/third-party-notices.md`

The generated inventory uses `NOASSERTION` for package license expressions because lock files do not carry
license metadata. Release reviewers must compare it with NuGet package metadata and dependency-review
results. Unknown or incomplete license evidence requires explicit review before release.

## SBOM and release artifacts

The release-prep workflow generates packages, release notes, a changelog, API compatibility reports,
Aspire deployment artifacts, a release manifest with SHA-256 package hashes, third-party attribution
artifacts, and a minimal SPDX 2.3 SBOM at `artifacts/release-prep/sbom.spdx.json`.

The repeatable local path is:

```bash
dotnet run --project tools/SharedKernel.Versioning.Tool -- \
  prepare-release \
  --version 0.1.0-alpha.local \
  --package-dir artifacts/packages/release-prep/0.1.0-alpha.local \
  --repo-root .
```

The SBOM is generated by repository-owned .NET tooling from resolved `packages.lock.json` files. It uses
SPDX `NOASSERTION` where lock files cannot prove license text.

## Package metadata

Packable projects should inherit repository metadata from `Directory.Build.props` unless they have a
documented exception:

- `Authors`: `ViajantesTurismo contributors`
- `Company`: `ViajantesTurismo`
- `Copyright`: `Copyright (c) 2025 ViajantesTurismo contributors`
- `PackageLicenseExpression`: `MIT`
- `RepositoryUrl`: `https://github.com/danigutsch/ViajantesTurismo`
- `PublishRepositoryUrl`: `true`

Every packable `SharedKernel.*` project must define:

- `PackageId`
- `Description`
- `PackageTags`

The release-prep workflow runs:

```bash
dotnet run --project tools/SharedKernel.Versioning.Tool -- validate-package-metadata
```

Do not replace SPDX package license metadata with embedded license files unless a package has a specific
non-standard licensing need.

## Community and support docs

Support routing is documented in [Support](../SUPPORT.md). Security disclosure stays in
[Security](../SECURITY.md).

`CODE_OF_CONDUCT.md` is intentionally deferred. Maintainers need to choose a public community conduct
policy and enforcement contact before adding one.

## Provenance and attestations

Current release provenance baseline:

- full Git history checkout for version calculation;
- release manifest with source SHA, package file names, sizes, and SHA-256 hashes;
- generated release notes and changelog;
- package metadata with repository URL and source-revision publishing;
- GitHub release and NuGet publishing only through manual `release` environment approval.

Public artifact attestations are deferred. Maintainers need to decide whether to adopt GitHub artifact
attestations, a SLSA-aligned workflow, or another provenance service before public stable package
publishing requires attestations.
